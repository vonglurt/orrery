The argument for doing it now

SSH and TLS want the same arithmetic

This is the structural fact that makes the rest of the plan tractable. Write the primitives once and the second protocol is a wire format rather than a cryptosystem.

The specification already exists

Nothing here is a judgement call

There is normally an argument at the start of a crypto module about which algorithms to support. That argument already happened, and it is committed.

src/profile.rs — written two phases early, at the request to lock the fleet down — is the whitelist, versioned, and it is already the thing that renders the node's sshd block. It names exactly one algorithm per slot. So phase 4 has no design space: the list of functions to write is a list somebody already reviewed, and a test called nothing_weak_is_on_any_list fails the build if it grows something with sha1, cbc, rc4, ssh-rsa, ecdsa or eighteen other tokens in it.

What that buys

No RSA. No NIST curves in key exchange. No CBC and no separate MAC, because both ciphers are AEAD. No TLS 1.2 record layer. No Diffie-Hellman group negotiation. Every one of those is a decoder that can be wrong and is not being written — the same argument rfb.rs made when it asked for Raw and CopyRect only, applied to a much larger surface.

Why it is the lowest risk, not the highest

Every line has a published answer

It is the largest single module in the plan, and it is the one least likely to go wrong — because unlike an RDP client negotiating with a server nobody here has run, every function in it has a known-correct output that somebody else wrote down.

A module where every line is checked against a vector somebody else published is either right or obviously wrong. That is a different risk profile from the rest of the wire, where correctness means agreeing with a live server about an ambiguous specification. Budget the time for phase 4; do not budget the worry.

Trap one

X25519's degenerate outputs

A shared secret of all zeros means the peer sent a small-order point, and an implementation that does not check produces a session key an attacker chose. Wycheproof has the exact inputs; the check is two lines and is the difference between key agreement and theatre.

Trap two

Ed25519's canonical S

Without a bounds check on the signature's second half, a valid signature can be transformed into a second, different, also-valid signature for the same message. For a host certificate that is a live malleability bug, and it is one line.

The discipline

Constant time, or it is decoration

A reviewer should be able to read crypto.rs looking for exactly two things: a branch that depends on a secret, and a table index that depends on a secret. Neither may exist. Concretely —

  • Field arithmetic over 2²⁵⁵−19 in 5×51-bit limbs, with no conditional reduction. The carry chain runs the same way every time regardless of the value.
  • Authentication tags compared by OR-accumulating a difference across all sixteen bytes, never by an early-returning loop. A comparison that stops at the first wrong byte tells an attacker how many bytes were right.
  • AES is bitsliced, not tabulated. A textbook T-table AES is a cache-timing oracle. The slower version is the only one worth writing.

Which is why ChaCha20-Poly1305 is the default

It is constant time by construction, and it is fast in software on a core with no AES instructions — and a Raspberry Pi Zero 2 has no AES instructions. AES-256-GCM is implemented only because an IronRDP server very likely insists on it for TLS. The cipher the console actually prefers is the one the hardware is good at.

The deliverable

What "done" means for phase 4

It ships with nothing visible

No new pixels. No new button. The verb bar still says 6 not built, because the transports that use these primitives are phases 5 through 8. This is the one phase whose deliverable is a test report, and saying so in advance is better than delivering one and calling it progress.

Acceptance

  • Every published vector in the table above passes, including the Wycheproof edge cases — not only the happy-path RFC examples.
  • cargo test stays green on macOS and under weston on Linux, and the module cross-compiles to aarch64-unknown-linux-musl.
  • [dependencies] is still empty. No #[link] is added — this is pure arithmetic and needs no system library at all, which makes it the first new module since ui.rs with no unsafe in it.
  • A measured throughput number for ChaCha20-Poly1305 on saskatchewan, because "fast enough on a Zero 2" is a claim this plan keeps making and has not yet checked.

Then the number starts falling

Phase 5 is ssh.rs, and it turns 6 not built into 5 — a real shell on a node, as the login user, with no password asked, because copal-prep.sh already installed the fleet-human principal that makes it possible. Phase 6 takes it to 3. The interface is finished; what happens now is that its buttons start appearing.

Stated rather than glossed

The risk that does not go away

R3 · hand-written cryptography

Test vectors and narrowness reduce the surface. They do not eliminate the risk, and this is not a reviewed library. The argument for doing it anyway is the same argument the whole repository rests on: a fleet node is on a LAN that invariant 6 says never reaches the internet, a dependency is a crate fetch that fails on the one machine this is for, and the gate is the fleet's certificate authority rather than this code.

A narrow list of hand-written primitives is a better bet than a wide one. It is not the same bet as rustls, and nothing in this brief should be read as claiming otherwise.
