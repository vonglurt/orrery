Abstract

A GTX 1080 Ti machine was taken from Omarchy (Arch) to Ubuntu 24.04 LTS, installed over the network from a Copal stick's boot menu, and made a CUDA node with one script, tools/cuda-node.sh, run over SSH from the Mac. The choices follow from the card. CUDA needs NVIDIA's own driver, whose user space is glibc-only, so not Copal (Alpine, musl). The 1080 Ti is Pascal: the 580 driver series is its last, and CUDA 12 its last toolkit. NVIDIA's CUDA repository for Ubuntu 26.04 carries only CUDA 13, so the release is 24.04. Ubuntu's installer, with "third-party" ticked, had already put in the 580-server driver with Ubuntu's prebuilt, signed kernel modules. The script keeps it, adds nvidia-smi, adds CUDA 12.9 from NVIDIA's repository at a priority too low for any of its driver packages to replace Ubuntu's, and ends with a CUDA program compiled for the card and run: on the first run, the 1080 Ti reported compute 6.1, 28 SMs and 10.9 GB, and added a million floats correctly. That run looked stopped for five minutes while it downloaded at 7.7 MB/s with its progress hidden; the script now shows it.

I. Objective

  1. Make the 1080 Ti machine run CUDA, on a setup NVIDIA supports for Pascal.
  2. Do it from the fleet's console machine over SSH, with one script that can be run again, on this node and the next.
  3. Record why each choice was made, for the next card.

IV. The script, tools/cuda-node.sh

Run on the node as root; every step checks before it acts, so it can be run again; everything it prints also goes to /var/log/cuda-node.log; a failed command that ends it prints STOPPED at line N with the command, as Copal's card build does.

  1. Checks: root; ID=ubuntu, VERSION_ID=24.04 (26.04 is refused, with the reason); an NVIDIA GPU on the PCI bus.
  2. Driver: finds the installed branch (nvidia-kernel-common-*), keeps it, and adds nvidia-utils-<branch> for nvidia-smi; with no driver, installs the headless 580-server branch with Ubuntu's prebuilt modules.
  3. NVIDIA's repository: cuda-keyring_1.1-1_all.deb, checked against a pinned sha256 (d2a6b11c…6dba, first use, 27 October) before dpkg -i; then the priority-100 pin.
  4. Toolkit: apt-get install -y cuda-toolkit-12-9.
  5. Paths: /etc/profile.d/cuda.sh puts /usr/local/cuda-12.9/bin on every login's PATH; /etc/ld.so.conf.d/cuda-orrery.conf and ldconfig for the libraries.
  6. The check: nvidia-smi (name, driver, memory, temperature); then a CUDA program written, compiled with nvcc -arch=native (for this card) and run: the device's name, compute capability, SM count and memory, and a vector add of 2^20 floats in managed memory, every element checked.

The toolkit step that looked stopped

After ==> CUDA toolkit 12.9 the screen showed nothing for five minutes, and Paul could find no activity. Read over SSH:

  • the processes: apt-get install -y -qq cuda-toolkit-12-9, running 5 min 13 s, with apt's https and http fetch methods alive;
  • /var/cache/apt/archives: 3.1 GB, 239 packages;
  • eno1: 3.16 GB received since boot;
  • measured over ten seconds: 77 MB received (7.7 MB/s), packages 239 → 244.

It was downloading, at a steady rate, with nothing on the screen: the script passed -qq to apt-get, which hides apt's own fetch lines. The script now installs the toolkit without -qq and says first that it is about 4 GB. The first run kept the old behaviour and finished normally.

The login: Copal fleet, not Ubuntu's advertising

Ubuntu's login offered help links, news from motd.ubuntu.com, "Enable ESM Apps to receive additional future security updates", and "New release '26.04.1 LTS' available. Run 'do-release-upgrade'": the last one the very upgrade this node must not take. tools/fleet-login.sh --role cuda, run on the node as root:

  • turns off, with chmod -x and a list kept for --undo: 10-help-text, 50-motd-news (and ENABLED=0 for its timer), 91-contract-ua-esm-status, 91-release-upgrade; and Ubuntu Pro's apt_news, which puts the ESM advertising into apt's own output;
  • keeps 50-landscape-sysinfo (load, memory, temperature, address), updates waiting, reboot required, firmware, and the HWE end-of-life notice;
  • adds 01-copal-fleet, run at each login, reading /etc/copal-fleet/node.conf: the fleet's name, the node and its role, the GPU as it is (name, driver, temperature, load, memory), CUDA's version, what is held and why, hints, and a warning against do-release-upgrade;

The first run stopped partway. On calber it silenced the five scripts and then exited without a word: the list it kept for --undo was built with cat old-list new-list | sort, and on a first run there is no old list, so cat failed, pipefail made the line fail, and set -e ended the script before it wrote node.conf, held the release or installed the banner. The list is gone (--undo turns every script in the silence list back on), and the script was then rehearsed whole on calber as user: a copy with every system path pointed into a scratch tree holding copies of calber's files, run to the end (five silenced, news off, Prompt=never, node.conf, fleet-status, the banner; exit 0), the banner run, and --undo run (all five back, news on). Only then was it handed back to be run as root.

topnotch

Paul named the panel topnotch ("like the simple script to show me system resources ... especially if they are more than 10% CPU"), and asked for copal-tm beside it: copal-tm (vonglurt/copal-tm) is the Copal task manager, a full-screen instrument panel and process browser; topnotch is the glance.

What changed from fleet-status:

  • CPU now, measured. ps's %CPU is a process's average over its life, so a job that went flat out a minute ago after an hour idle barely shows. topnotch reads every process's CPU ticks (/proc/PID/stat, utime plus stime, parsed after the ) that ends a name that may hold spaces) twice, half a second apart, as htop does.
  • Busy now: every process over 10% of a core in that half second, busiest first, with its user, memory, and the address it was started from if an SSH session started it.
  • the SSH table shows CPU now, sorted by it.
  • a hint for copal-tm: the command if it is installed, else how to install it (cargo install copal-tm; installing from crates.io on the node was left to Paul, who wrote it).

VI. Discussion

Ubuntu's installer did half the work. "Third-party" put in the right driver branch, built and signed by Ubuntu for the running kernel, which is what a node needs to survive its own updates. What a script had to add was the part Ubuntu does not ship (NVIDIA's toolkit) and a guard against the part that could go wrong later (NVIDIA's repository offering a driver without Pascal).

Silence is not a stop, and a stop is not silence. The same lesson as the card build on saskatchewan the same day, from the other side: there, a stop printed nothing; here, progress printed nothing. Both are answered the same way: say what is happening, keep a log, and when unsure, measure the machine (bytes received, packages fetched) before concluding.

Toward a fleet verb. The node is Ubuntu, so it is not in copal fleet state and orrery cannot see it. The script is the first form of a verb ("make this a CUDA node"), run by hand over SSH. To be a verb of the console, the fleet needs a way to hold a non-Copal node, its address, account and role, and that is a decision for the fleet's design, not this script.

The second node, boburner

28 October 2026. boburner is 192.168.8.113:

  • Ryzen 7 3700X, 16 threads, 31 GB;
  • GTX 1070 Ti (Pascal, compute 6.1, 8 GB);
  • an Ubuntu 24.04 desktop with a ZFS pool (Hexamir) and VirtualBox.

It came with Ubuntu's 535 driver and was months behind.

1. The upgrade that would not finish.

  • apt-get upgrade held back the NVIDIA packages and the HWE kernel meta-packages. Four packages were left half-installed: 24.04's HWE kernel, which is now 7.0 (7.0.0-38), and its headers.
  • Its DKMS step failed. zfs-dkms 2.2.2 does not configure on 7.0 (bdev_open_by_path() exists... configure: error), and virtualbox-dkms 7.0.16 does not build.
  • A machine whose ZFS pool and VMs depend on DKMS modules stays on the standard 6.8 line. So the HWE kernel and its meta-packages were purged, and linux-generic (6.8.0-147) put in their place.
  • No dist-upgrade.

2. The driver: 535 is now a name for 580.

  • Ubuntu's nvidia-driver-535, nvidia-utils-535, nvidia-kernel-common-535 and linux-modules-nvidia-535-generic are now transitional packages. Each depends on its 580 counterpart.
  • So apt-get install linux-generic linux-modules-nvidia-535-generic nvidia-driver-535 (08:33, from /var/log/apt/history.log) installed driver 580.178.04, with Ubuntu's prebuilt, signed module for 6.8.0-147 (linux-modules-nvidia-580-generic). After the reboot:
$ uname -r
6.8.0-147-generic
$ cat /proc/driver/nvidia/version
NVRM version: NVIDIA UNIX x86_64 Kernel Module  580.178.04

This is the desktop 580 branch, not calber's 580-server. Both are the same driver version, from Ubuntu's archive. ZFS and VirtualBox rebuilt for 6.8.0-147, and the pool is mounted.

3. Chrome's repository. It failed its signature check (NO_PUBKEY FD533C07C264648F) and served a 404 for a version that is gone. apt-get purge google-chrome-stable removed the package and its repository list. Then apt-get upgrade finished, leaving 2 packages phased: fwupd and linux-firmware.

4. cuda-node.sh: right result, wrong report. It ran twice (15:38Z and 15:56Z). Both runs printed:

    installed branch: 535 (asked for 580-server); keeping what is there
    branch 535: a GTX 900 or 10 series card needs 580; newer cards are fine on it too
...
NVIDIA GeForce GTX 1070 Ti, 580.178.04, 8192 MiB, 36
device: NVIDIA GeForce GTX 1070 Ti, compute 6.1, 19 SMs, 7.9 GB
vector add of 1048576 floats: correct
==> Done: boburner is a CUDA node (driver 535, CUDA 12.9).
  • CUDA 12.9 works: nvcc 12.9.86 compiled for sm_61 and ran on the card.
  • But the script names the wrong branch.
    • It takes the first nvidia-kernel-common-* package dpkg lists, and

    the transitional -535 sorts before -580.

    • Its own nvidia-smi line two steps later says 580.178.04.
    • It also installed nvidia-utils-535, a transitional name for what

    was there.

  • The fix: read the branch from the loaded module (/proc/driver/nvidia/version), or from nvidia-smi, not from package names.
  • An earlier note here (the same day) said the toolkit could not run on 535. That was not what happened: the card was on 580 throughout the script's runs. It is also not true in general, because CUDA 12's minor-version compatibility runs sm_61 code built by 12.9 on a 525+ driver.
  • nvcc 12.9 warns that offline compilation for targets before sm_75 will be removed in a future release. On a Pascal card CUDA 12.9 is the last toolkit, as section III says.

What is left behind, harmless.

  • The four transitional 535 packages. To remove them, mark the 580 ones manual first (apt-mark manual nvidia-driver-580 nvidia-utils-580 linux-modules-nvidia-580-generic), then purge the 535 names.
  • The module for the fallback kernel 6.8.0-52 (linux-modules-nvidia-535-6.8.0-52-generic).
  • Config-only (rc) entries of old 535 modules.
  • A dkms status warning that the zfs module built for 6.8.0-147 differs from the installed one. The kernel ships its own zfs 2.2.2 module beside zfs-dkms's.
